## 3.2 Account

### 3.2.1 Account CR

The `Account` CR holds the details about the AWS account that was created, where the account is in the process of becoming ready, and whether it is linked to an `AccountClaim`, i.e., claimed.

```yaml
apiVersion: aws.managed.openshift.io/v1alpha1
kind: Account
metadata:
  name: osd-{accountName}
  namespace: aws-account-operator
spec:
  awsAccountID: "0000000000"
  claimLink: example-link
  iamUserSecret: osd-{accountName}-secret
```

### 3.2.2 Account Controller

The `Account` controller is triggered by creating or changing an `Account` CR. It is responsible for the following behaviors:

If the **awsLimit** set in the constants is not exceeded:

1. Creates a new account in the organization belonging to credentials in secret `aws-account-operator-credentials`
2. Configures two AWS IAM users from `iamUserNameUHC` as their respective username
   - Creates IAM user in new account
   - Attaches Admin policy
   - Generates a secret access key for the user
   - Stores user secret in an AWS secret
3. Creates STS CLI tokens
4. Creates and Destroys EC2 instances
5. Creates AWS support case to increase account limits

**Note:**

- `iamUserNameUHC` is used by Hive to provision clusters

#### Additional Functionality

- If `status.RotateCredentials == true` **or** the annotation `aws.managed.openshift.com/rotate-credentials: "true"` is set, the account-controller will rotate the IAM access key for the managed IAM user (`osdManagedAdmin-<id>`). The K8s secret named in `spec.iamUserSecret` is updated with the new key. See [Credential Rotation](#credential-rotation) below.
- If the account's `status.State == "Creating"` and the account is older than the `createPendTime` constant the account will be put into a `failed` state.
- If the account's `status.State == AccountReady && spec.ClaimLink != ""` it sets `status.Claimed = true`.

#### Spec

Updates the Account CR

```yaml
spec:
  awsAccountID: "000000112120"
  claimLink: "claim-name"
  iamUserSecret: accountName-secret
```

- `awsAccountID` is updated with the account ID of the AWS account that is created by the `Account` controller.
- `claimLink` holds the name of the `AccountClaim` that has claimed this `Account` CR.
- `iamUserSecret` holds the name of the secret containing IAM user credentials for the AWS account.

#### Status

Updates the Account CR:

```yaml
status:
  claimed: false
  conditions:
    - lastProbeTime: 2019-07-18T22:04:38Z
      lastTransitionTime: 2019-07-18T22:04:38Z
      message: Attempting to create account
      reason: Creating
      status: "True"
      type: Creating
  rotateCredentials: false
  lastCredentialRotationAt: "2024-01-15T10:30:00Z"
  state: Failed
  supportCaseID: "00000000"
```

**state** can be any of the account states defined in the constants below:

- `AccountPending` indicates an account is pending.
- `AccountCreating` indicates an account is being created.
- `AccountFailed` indicates account creation has failed.
- `AccountReady` indicates account creation is ready.
- `AccountPendingVerification` indicates verification (of AWS limits and Enterprise Support) is pending.

* `claimed` is true if `currentAcctInstance.Status.State == AccountReady && currentAcctInstance.Spec.ClaimLink != ""`
* `rotateCredentials` is set to `true` during account reuse (when an AccountClaim is deleted and the account is returned to the pool) to trigger IAM credential rotation before the account is reused. Cleared automatically after rotation completes or fails.
* `lastCredentialRotationAt` records the timestamp of the last successful IAM credential rotation. Empty if credentials have never been explicitly rotated.
* `supportCaseID` is the ID of the aws support case to increase limits.
* `conditions` indicates the last state the account had and supporting details. Credential rotation adds two condition types:
  - `CredentialRotationInProgress` — set while rotation is running.
  - `CredentialRotationFailed` — set when rotation fails (e.g. the IAM user already has 2 access keys). The account remains `Ready`; a human must resolve the issue before retrying.

#### Credential Rotation

IAM credentials for the managed IAM user (`osdManagedAdmin-<id>`) can be rotated in two ways:

**Automatic (account reuse):** When an `AccountClaim` is deleted, the `accountclaim` controller sets `status.RotateCredentials = true`. On the next reconcile the account-controller rotates the credentials and clears the flag before the account is returned to the pool.

**Manual (annotation):** Set the annotation on a Ready, non-STS, non-BYOC account:

```bash
oc annotate account <account-name> aws.managed.openshift.com/rotate-credentials=true -n aws-account-operator
```

The annotation is removed automatically after rotation completes or fails.

**Rotation strategy:** The controller uses a create-before-delete approach — a new access key is created first, the K8s secret is updated, and then the old key is deleted. This ensures there is never a window with zero valid credentials.

**2-key limit:** AWS allows at most 2 access keys per IAM user. If the user already has 2 keys when rotation is triggered, the controller sets the `CredentialRotationFailed` condition with reason `AccessKeyLimitReached`. For reuse-triggered rotation, the controller retries automatically every 5 minutes. To resolve immediately, use the force annotation:

```bash
oc annotate account <account-name> aws.managed.openshift.com/force-rotate-credentials=true -n aws-account-operator
```

The force annotation deletes **all** existing access keys before creating a new one, bypassing the 2-key count check. It also bypasses the 5-minute retry back-off. Use it only when the `AccessKeyLimitReached` condition is set and you want immediate recovery rather than waiting for the next retry.

> **⚠️ Warning — OSD classic clusters (Mint / Passthrough CCO mode)**
>
> When an OSD classic cluster is provisioned using the `osdManagedAdmin` credentials, the OpenShift
> installer passes those credentials to the Cloud Credential Operator (CCO), which stores them as a
> long-lived secret inside the cluster (typically `kube-system/aws-creds`). CCO uses that secret in
> Mint mode to create and rotate per-component IAM users on demand.
>
> **Rotating the `osdManagedAdmin` IAM access key via AAO does not update `kube-system/aws-creds`
> inside any running OSD classic cluster.** After the old key is deleted:
>
> - CCO loses the ability to mint new per-component credentials.
> - Any CCO-managed component that attempts to refresh its credentials will fail.
> - New cluster installs using the same account will fail until `kube-system/aws-creds` is updated.
>
> **Before rotating credentials on an account that backs OSD classic clusters:**
>
> 1. Identify all running OSD classic clusters provisioned against this account.
> 2. After AAO updates the K8s secret (`spec.iamUserSecret`), patch `kube-system/aws-creds` on
>    each affected cluster with the new access key ID and secret access key.
> 3. Restart the CCO pod (`openshift-cloud-credential-operator` namespace) on each cluster to pick
>    up the new credentials.
>
> This coordination step is **not automated** by AAO. For ROSA HCP / HyperShift clusters using
> STS / Manual CCO mode, no action is needed — those clusters obtain credentials via OIDC pod
> identity and do not hold long-lived copies of the `osdManagedAdmin` keys.
